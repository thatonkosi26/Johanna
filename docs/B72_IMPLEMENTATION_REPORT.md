## 2. Module structure

Layered (each module imports only lower layers; the nine late-bound references to higher layers go
through `modules/hooks.js`, filled once by `app.js` after all modules evaluated):

| Layer | Module | Lines | Content |
|---|---|---:|---|
| 0 | `hooks.js` | 3 | late-bound references |
| 1 | `state.js` | 135 | constants, `NAV_SECTIONS`, `ROUTE_ALIASES`, the single `state` object |
| 2 | `format.js` | 121 | escaping, time formatting, chips, `setInner`, page heading |
| 3 | `status.js` | 73 | market/quote status derivations |
| 4 | `api.js` | 43 | `fetchJson`, `tradeGet`, error shapes |
| 5 | `components.js` | 128 | status vocabulary, `statusBand`, `inactivePanel` (new) |
| 6–9 | `quotes.js` 96, `chart.js` 481, `analysis.js` 391, `overlay.js` 779 | | market screens (moved unchanged) |
| 10–15 | `panels.js` 58, `account.js` 155, `risk.js` 179, `decisions.js` 84, `trades.js` 353, `shadow.js` 275 | | existing screens |
| 16–18 | `control.js` 161, `positions.js` 24, `evidence.js` 23 | | new read-only screens and the operations loader |
| 19–24 | `settings.js` 32, `overview.js` 170, `pages.js` 80, `data.js` 64, `polling.js` 238, `navigation.js` 80 | | settings, Overview, router, dashboard load, pollers, navigation |
| top | `app.js` | 136 | event listeners (one set), routing, startup, hook registration |

Method: the split was generated by a scanner that moves each top-level declaration unchanged with
its comments and creates imports from actual references (strings, templates and comments are
skipped). It was verified before any feature work: **166/166 browser tests passed on the split
code alone**. A validator confirmed every imported name is exported and that there is no cycle.
Behaviour-preserving adjustments: the former theme wrapper (`render = themedRender`, impossible
with read-only import bindings) became `applyTheme()` as `render()`'s first statement; the test
diagnostics previously available as page globals are exposed explicitly on `window` (state,
pollers, chart helpers — read-only use by tests); explicit call counters
(`state.drawChartCalls`, `state.overlay.modelCalls`) replace two tests' function wrappers with
the same assertions.

State, pollers and listeners are not duplicated: one `state` object (`state.js`), one
`livePolling` (`polling.js`), event listeners registered once in `app.js` (chart pointer/wheel
listeners stay in `chart.js` where their drag state lives). Polling intervals, page-specific
polling, visibility handling, overlap prevention, backoff, cached/stale handling, idempotent trade
writes and escaping are untouched code.

## 4. Overview components

- **Status band** (8 cells, each linking to its screen): Application (ONLINE / DEGRADED /
  OFFLINE from `/api/dashboard`), Market data (CURRENT / STALE / CACHED / UNAVAILABLE), Journal
  (READY / ATTENTION / UNAVAILABLE), Schema (installed vs registered), Execution (DISABLED unless
  the backend reports otherwise), Unattended operation, Scheduler (ON / OFF), CostTerms
  (NOT CONFIGURED / CONFIGURED). Values not loaded are NOT CHECKED; failed or unestablished values
  are UNAVAILABLE; nothing defaults to a positive state. Freshness line: dashboard receipt time and
  readiness `checked_at_utc`.
- **Market summary**: existing quote strip, chart, watchlist, market information, calendar and
  compact analysis — same pollers, no new MT5 request.
- **Account**: balance, equity, free margin with validation chips and retrieval time **only if
  already read on Account & Broker**; otherwise NOT LOADED with a link.
- **Decisions & risk**: latest six decisions (journal read) with analysis, risk, eligibility and
  execution kept separate; the current risk proposal only if already evaluated (status label and
  the blocking reason when there is no actionable volume), otherwise NOT CHECKED.
- **Trade journal**: open / partially closed / closed / voided counts, today's net realised result
  only for trades fully closed today with a calculated net result, trades with exits today not
  included, trades with incomplete accounting — **only from a list already loaded by the Trade
  Journal screen** (see section 8); otherwise NOT LOADED.
- **Operational notices**: unattended not permitted, each readiness blocker (costs, scheduler,
  monitoring, notifications, execution), automatic backups disabled, any check needing attention.

## 5. System Control Centre components

Status band; **Readiness** (manual operation, unattended operation, assessment time, blockers,
checks with OK / ATTENTION / UNAVAILABLE / NOT CHECKED); **Service status** (scheduler,
monitoring, reconciliation, notifications, automatic backups, evidence recording, user-confirmed
linking, autonomous execution, CostTerms — each with state, source and note; sources are either
"live · readiness" or "by design · no status API yet"); **Journal and schema** (journal, schema,
pending change, audit chain, key, valid backup pairs); **Scheduler** (read-only, purpose,
"activation requires separate approval"); **Notifications** (INACTIVE); **Backups and recovery**
(automatic backups DISABLED, verified recovery points count, history / restore rehearsal NOT
AVAILABLE — no API); **Operational restrictions**. No activation, backup, restore,
acknowledgement, confirmation or approval control exists.

## 6. Safety corrections

| Correction | Result |
|---|---|
| Autonomous execution | `#execution-toggle` and its click handler removed; Settings shows "Autonomous execution is disabled. Johanna does not have authorisation to execute trades autonomously." The UI never writes `autonomous_execution_enabled`; stored values are preserved; the top bar shows Disabled (a saved preference is explained in a tooltip, never as "on") |
| Operating mode | the "Autonomous preference" select and handler removed; read-only "Manual"; a saved non-manual value is described as having no effect; the top-bar mode label is MANUAL |
| Scheduler | enable/disable button and `setShadowEnabled()` removed — no frontend code path can POST `/api/shadow/scheduler`; read-only state and explanation on Shadow research and Control Centre |
| Readiness vocabulary | OK / ATTENTION / UNAVAILABLE / NOT CHECKED (shadow cycle statuses unchanged) |
| Stale journal label | `JournalStore.status()["monitoring_and_reconciliation"]` now `reported_by_monitoring_service` (the journal stores records but cannot know activation); the Decisions page no longer shows the old "not implemented" clause; the Control Centre shows ACTIVE / INACTIVE / NOT AVAILABLE from the monitoring service |

The backend preference API is unchanged (compatibility); the persistence layer still validates
`operating_mode` and the boolean; broker execution remains `DisabledExecutionService`.

## 11. Known issues and limitations

- Automatic backups, evidence recording and user-confirmed linking are shown from the current
  release's design ("by design · no status API yet"), not from a live status endpoint; read-only
  APIs are planned for B7.5 / B7.6.
- Overview account, risk and trade summaries appear only after their own screens have loaded the
  data in the session (deliberate: no new MT5 reads).
- The tablet sidebar is labelled (206 px) instead of the former icon strip.
- The previously reported browser-test snapshot race
  (`test_repeated_toggling_adds_no_requests_timers_or_listeners`): __RACE__
- `app.js` still carries the ~30 test diagnostics on `window` (explicit, read-only use by the
  browser tests).

## 12. Production and operational boundaries

No backend start, stop or restart; no production journal, key, backup or `data/` access (tests
use temporary directories); no migration; no MT5 call (in-process fake only); no broker action;
scheduler, monitoring, reconciliation, notifications, automatic backups and evidence recording not
activated; autonomous execution not enabled; CostTerms and risk policy unchanged; no production
preference changed; no Git command; no dependency installed.

**Important for the running backend (not verified against production — derived from the code).**
The backend reads frontend files from disk on every request, but its static-asset allowlist is
the one loaded in memory at its last start (`app.js`, `styles.css` only). After this change a
browser **reload** of the open dashboard receives the new `index.html` and `app.js`, whose imports
of `/assets/modules/*.js` the running process answers with 404 — the dashboard would stop loading
("Loading workstation state") until the backend is restarted from this source tree. An already
open, not reloaded page keeps working. A restart deploys only the B7.2 backend changes (the asset
allowlist and the journal status wording); it migrates nothing (schema v6 is already installed).
Restarting remains your decision.
