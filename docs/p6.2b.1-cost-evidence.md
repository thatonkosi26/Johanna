# P6.2b.1 — Cost evidence, holding periods and broker rollover

Status: implemented and tested offline. **No production cost, slippage allowance or holding
period is configured or approved.** Production `COST_TERMS` is empty, so every risk proposal
remains `UNVERIFIED` with no actionable volume, exactly as before.

Code: `src/johanna/cost_evidence.py` (pure), used by `src/johanna/risk_engine.py`
(`RISK_ENGINE_VERSION` 3). Tests: `tests/test_cost_evidence.py`.

## Broker rollover

| Item | Treatment |
|---|---|
| Source | Exness Help Centre, "About swap": swap applied on weekdays at 21:00 GMT (summer) / 22:00 GMT (winter), triple on Wednesday for forex. Read via search summaries during P6.2b (the Help Centre refuses automated fetching); verbatim text not yet retrieved. |
| Interpretation | 21:00/22:00 GMT is exactly **17:00 America/New_York** under US daylight-saving rules (the industry rollover convention). Primary schedule: 17:00 New York, Monday–Friday. |
| Seasonal ambiguity | Exness does not say whose "summer" applies. When US and UK clocks differ (about three weeks in March, one in late October/early November) the alternative reading, 22:00 Europe/London, is also computed and the **larger** charge count is used. The result reports `seasonal_ambiguity`. |
| Triple day | Read live from MT5 (`swap_rollover3days`); currently Wednesday for EURUSDc, GBPUSDc, USDJPYc. A non-weekday value fails closed. |
| Counting | Rollovers at or after the evaluation time and up to the end of the holding window, each counted once; an event exactly at the evaluation instant counts (conservative). None on Saturday or Sunday. |
| Holidays | **Not modelled.** No reliable source for holiday rescheduling; every swap result states `holiday_adjustments: not_modelled`. |
| Rates | Always the live MT5 `swap_long` / `swap_short`; never configured or cached. Credits and zero rates never reduce risk. |

The previous model counted rollovers at UTC midnight, so between 21:00/22:00 UTC and
midnight it counted a rollover that had already happened (e.g. Tuesday 22:30 UTC counted
Tuesday's single charge instead of Wednesday's triple). That defect is corrected.

## Holding assumptions (per timeframe)

`HoldingAssumption(timeframe, max_hours, rationale, status, effective_utc, policy_version,
approved_at_utc)`. Status `PROPOSED` | `APPROVED` | `REJECTED`. Only an `APPROVED`
assumption, effective and approved within 30 days, is used; otherwise a swap that is a cost
keeps the proposal `UNVERIFIED`. No default is ever substituted.

Draft proposals (`HOLDING_PROPOSALS`, status `PROPOSED`, **not policy**): H1 24 h, H4 5 days
(120 h), D1 20 days (480 h).

A holding assumption only bounds the swap *estimate*. It is not a time stop: nothing closes,
modifies or monitors positions.

## Cost components

`CostComponent` (commission or slippage) — every field explicit, nothing inferred:

| Field | Rule |
|---|---|
| value | finite, ≥ 0 (no NaN, infinity, booleans) |
| currency | commission: `USC` or `USD`; slippage: none (points/pips) |
| unit | commission: `amount_per_lot` (per 1.0 lot); slippage: `points` or `pips` |
| basis | `per_side` or `round_trip` |
| instruments | non-empty tuple of supported broker symbols, no duplicates |
| account_type | `exness_standard_cent` |
| source_reference, source_description | required |
| evidence_date, effective_utc | timezone-aware |
| status | `VERIFIED`, `UNVERIFIED`, `PROVISIONAL`, `REJECTED` (`EXPIRED` derived) |
| approved_at_utc | required for `VERIFIED`; not before the evidence date |

Usable only when `VERIFIED`, effective, approved at most 30 days before the evaluation and
covering the instrument. Each component is assessed independently; a missing record is
`MISSING`, never zero. Two records for the same cost and instrument are refused.

Conversions are recorded step by step and shown per lot and per 0.01 lot:
USD → USC × 100; per side → round trip × 2; pips → points × 10 (5- and 3-digit quotes only).
